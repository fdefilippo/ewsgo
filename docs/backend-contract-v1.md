# EWSGo backend contract v1

EWSGo frontends call the protocol-independent Go interfaces in
[`internal/core`](../internal/core). This document versions the Mail profile
and its optional extensions. Adapters are compiled with the gateway from
source. A backend can use its own native API and storage model.

## Mail profile

| Contract | Adapter responsibility |
| --- | --- |
| `Authenticator`, `Session` | Authenticate to the configured backend. Return the backend-resolved display name and stable account scope. Release the native session and credentials when it closes. Resolve the scope solely through authenticated backend credentials. |
| `Mailbox.Root`, `Get` | Return the same root ID on subsequent logins and expose a root folder with an empty parent. Resolve IDs in that authenticated scope and check membership when it is part of the ID. |
| `Mailbox.Query` | For direct folders and messages, apply the supplied parent and return bounded pages. If `More` is set, `NextOffset` advances. Equality filters and ordering need independent support. |
| `Object`, `Patch` | Use typed properties, a stable opaque ID, the current parent and an opaque revision. Missing properties remain absent. Release or clone mutable buffers at interface boundaries. |
| `MIMEReader` or embedded MIME | Return complete MIME or an error. The bytes represent the backend's stored message. Respect bounded reads and access checks. |
| Generic edits and deletion | Use the `Capabilities` flags for these methods. `Edit.Apply` stages private changes and `Commit` checks the expected revision and commits atomically within the provider. Specialized write interfaces define their own guarantees. |

The gateway binds each account scope to a stable backend instance. An
installation must keep that binding stable across restarts. Client IDs and
cursors are generated by the gateway and tied to this binding. Keep ID,
revision, native cursor and client token distinct. A multi-placement
backend such as JMAP can project one stable folder-specific ID per
membership while retaining the native message identity.

## Optional capabilities

Use the smallest interface that expresses the operation. Examples include
`MailAttachmentReader` for decoded file data, `MailDraftWriter` and
`MailMessagePlacementWriter` for writes, `Directory` for address resolution,
and the separate contacts, appointments, sharing and notification
interfaces. The presence of an optional interface is evaluated per session.
Backend ACLs can still deny an individual operation. The generic
`Capabilities.Write` flag applies only to `Edit`. Evaluate specialized mutations through their own interfaces.

The persistent frontend consumes the native synchronization journal through
`NativeProjectionStore`. A backend refresh reads an opaque native checkpoint,
then commits observed changes, verified removals and the next checkpoint
atomically. Reconciliation needs a complete, verifiable source baseline.
A missing item on a partial page is insufficient evidence for deletion.
When remote state changes during observation, discard the batch and retry
from the committed checkpoint. A native journal may expire. The adapter
reconciles the source before advancing the local cursor. Limited or
incomplete observations return an error to the caller. A frontend may
instead use `Mailbox.Changes` or `FolderSync` where configured.

`MailSendBackend` separates staging from dispatch. The gateway claims a
submission intent durably before invoking the dispatch function. Definitive
rejections and failures known to precede dispatch have dedicated errors.
A possibly accepted dispatch remains uncertain and is never automatically
retried. An observed copy in Sent Items is advisory evidence. Native
acceptance establishes submission, while delivery is established by the
recipient's system.

## Error semantics

Return core errors so callers can use `errors.Is`. Keep raw upstream
responses and credentials outside frontend errors and logs.

| Core outcome | Meaning and EWS result |
| --- | --- |
| `ErrNotFound` | Object absent in the authorized lookup. EWS returns the operation's item or folder not-found code. |
| `ErrAuthentication`, `ErrAccessDenied` | Native login rejected or scope/operation denied. The HTTP authentication layer challenges failed credentials. EWS access checks return `ErrorAccessDenied`. |
| `ErrUnsupported` | Capability unavailable. The Mail write and sync handlers map it to `ErrorInvalidPropertyForOperation`. Frontends can also omit a protocol endpoint or capability entirely. |
| `ErrInvalid`, `ErrLimit` | Malformed semantic input or a supported limit exceeded. EWS returns `ErrorInvalidRequest` or a size/limit code for the operation. |
| `ErrConflict`, `ErrResync` | Stale revision or unusable cursor. For example, EWS writes return `ErrorIrresolvableConflict` and expired EWS sync states return `ErrorInvalidSyncStateData`. |
| `ErrOutcomeUnknown` | A write might already have committed. Preserve that uncertainty and the relevant intent. EWS returns `ErrorInternalServerError` for a submission it cannot confirm. |

## Implement and verify an adapter

1. Add a package under `internal/backend`. Wire an explicit backend
   selector at the service boundary. Keep native transports and data
   types in that package, and wire TLS trust for the server.
2. Implement the Mail profile for personal mailboxes. Start with folder
   roles, pagination, scope and MIME. Implement optional interfaces only
   when the backend can meet their semantics.
3. Run the shared [Mail conformance suite](../internal/backend/conformance).
   Give it an authenticated synthetic account, an Inbox fixture with a
   binary attachment, and the expected MIME when byte-for-byte import is
   guaranteed. Its default target is the in-memory provider. The live
   targets exercise the same checks on Zimbra and JMAP.
4. Qualify native synchronization and any optional write through the
   intended frontend. Test restarts, invalid state, inaccessible objects,
   uncertain outcomes and absent capabilities. Record the server,
   configuration and observed operations with the result.

Additive optional interfaces and properties may be added in v1. An adapter
compiled for v1 can leave them unimplemented. Changes to required method
signatures, scope, identity, cursor or error semantics require a new
contract version, an adapter migration and a strategy for persisted state.
Qualify each frontend separately. A Mail profile run alone establishes
neither MAPI nor groupware interoperability.

### Running the live Mail profile

The live tests use HTTPS and isolated synthetic accounts. The credentials
files use the owner-only `url:`, `user:` and `pass:` format. In the Zimbra
Inbox, place a message with Message-ID `<backend-contract-zimbra@example.invalid>`
and attachment `fixture.bin`. Set `EWSGO_CONFORMANCE_ZIMBRA_MESSAGE_ID` to
reuse a fixture with a different Message-ID. In the JMAP Inbox, place a
message with Message-ID `<backend-contract-jmap@example.invalid>` and
attachment `contract.bin`. Both attachments contain the bytes 0 through
255. If the JMAP fixture MIME file is available, provide it for an exact
comparison.

```sh
EWSGO_CONFORMANCE_ZIMBRA_CREDENTIALS=/private/zimbra.env \
EWSGO_CONFORMANCE_ZIMBRA_CA=/private/zimbra-ca.pem \
EWSGO_CONFORMANCE_JMAP_CREDENTIALS=/private/jmap.env \
EWSGO_CONFORMANCE_JMAP_CA=/private/jmap-ca.pem \
EWSGO_CONFORMANCE_JMAP_MIME=/private/jmap-fixture.eml \
go test ./internal/backend/conformance -run TestBackendMailContract -v -count=1
```
